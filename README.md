# Order Sync API

Сервис для синхронизации заявок из внешнего источника, нормализации телефонов, дедупликации клиентов и расчёта итоговой статистики.

## 1. Назначение

API получает массив заявок с URL `https://test.ooobs.ru/api/orders`, нормализует номера телефонов, отбрасывает невалидные записи, объединяет дубликаты по телефону и возвращает итоговый список клиентов в строго заданном формате.

## 2. Архитектура

Проект построен в компактной структуре:

- `app/config.py` — параметры окружения и таймауты.
- `app/client.py` — HTTP-клиент для внешнего API.
- `app/normalizer.py` — чистая функция нормализации телефона.
- `app/service.py` — бизнес-логика фильтрации, дедупликации и статистики.
- `app/schemas.py` — Pydantic-модели для JSON-ответа.
- `app/main.py` — FastAPI-приложение и маршруты.
- `tests/` — автоматические тесты.

Сервис не хранит данные в БД и работает как чистое преобразование входного массива в результат, что обеспечивает идемпотентность при одинаковом входе.

## 5. Локальный запуск

Создайте виртуальное окружение:

```bash
python -m venv .venv
```

Активация:

Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Linux/macOS:

```bash
source .venv/bin/activate
```

Установите зависимости:

```bash
pip install -r requirements.txt
```

Запустите сервис:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

После запуска доступны:

- http://localhost:8000/
- http://localhost:8000/health
- http://localhost:8000/api/clients
- http://localhost:8000/docs

## 8. Правила нормализации телефонов

Функция `normalize_phone` преобразует номер в канонический формат `+7XXXXXXXXXX`.

Примеры:

- `+7 (999) 123-45-67` → `+79991234567`
- `8 (999) 123-45-67` → `+79991234567`
- `89991234567` → `+79991234567`
- `79991234567` → `+79991234567`
- `9991234567` → `+79991234567`
- `+7-999-123-45-67` → `+79991234567`

Номера с 10 цифрами получают префикс `+7`. Номера с 11 цифрами принимаются только при корректном русском префиксе `7` или `8`.

Некорректные значения возвращают `None`, например:

- пустая строка;
- строка только из пробелов;
- значения с буквами;
- номера с слишком длинной/короткой последовательностью;
- числа вместо строк;
- неподдерживаемый префикс;
- строки с несколькими знаками `+`;
- явный мусор.

## 9. Правила дедупликации

Для каждой группы заявок с одинаковым нормализованным телефоном выбирается победитель по следующему порядку:

1. максимальный `amount`;
2. более поздний `created_at`;
3. детерминированное дополнительное правило по `id` при равенстве;
4. стабильный индекс записи как последний резерв.

Если `amount` или дата невалидны, сервис не падает, а применяет безопасную политику обхода и продолжает обработку массива.

Для дат без часового пояса применена политика: считаем их UTC, чтобы не смешивать aware- и naive-datetime и не падать на сравнении.

## 10. Расчёт статистики

- `received = len(raw_orders)`
- `invalid_dropped = количество заявок с невалидным телефоном`
- `unique = len(clients)`
- `duplicates_merged = received - invalid_dropped - unique`

Проверка:

```text
duplicates_merged = received - invalid_dropped - unique
```

Если массив пустой, все счётчики равны нулю, а `clients` — пустой массив.

## 11. Обработка ошибок

Сервис отдельно разделяет:

- ошибки интеграции с внешним API;
- ошибки отдельной записи в массиве.

Если источник недоступен, возвращает HTTP 503. Если ответ отличается от контракта (невалидный JSON, неправильный корневой тип, HTTP ошибка), возвращает HTTP 502.

Подробности логируются без персональных данных (нет тел., email, имён), а клиент получает безопасное сообщение без traceback.

Для деплоя на Render:

5. Проверьте переменные окружения: `ORDERS_SOURCE_URL`, `REQUEST_TIMEOUT`, `LOG_LEVEL`.

Пример команды запуска:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 10000
```

## 15. Известные ограничения

- Сервис является статичным и пересчитывает данные при каждом запросе без хранения в БД — это соответствует задаче, но не подходит для исторических архивов.
- Нормализация телефона придерживается российских правил и не реализует полноценную справочную систему по всем международным сценариям.
- Публичный деплой не был выполнен в этой сессии, потому что не предоставлены реальные учётные данные Render или доступ к хостингу. Конфигурация для деплоя подготовлена и готова к использованию после авторизации.
